## Overview

This folder contains Claude Code slash-command definitions: single-purpose Markdown files with YAML frontmatter that package reusable prompts into invokable workflows. Commands are organized by group, and the group folder is the command namespace: drafting utilities live under `drafting/`, the commit command under `git/`, helper utilities under `helper/`, implementation commands under `implement/`, command-building helpers under `meta/`, planning commands under `plan/`, review-chain commands under `review/`, and validation commands under `validate/`. A file `git/commit.md` is invoked as `/git:commit`.

Each active command should follow the INPUT -> PROCESS -> OUTPUT framework: declare its argument contract, identify context to load, define ordered process steps, state decision discipline, and produce exactly one output type, either a Human-Readable Report or a Structured Agent Handoff. To invoke these commands in Codex, use: "Read and follow in full `<command_path>` with this additional context:".

## Key Features

- Reusable prompts packaged as slash-command Markdown files with explicit argument contracts
- Folder-level organization for planning, execution, review, and meta-authoring workflows
- YAML frontmatter declaring descriptions, argument hints, and least-privilege tool access where needed
- Meta-commands for creating new commands and sub-agents from shared templates
- Strict INPUT -> PROCESS -> OUTPUT discipline so outputs can be checked by humans or handed to downstream agents

## Documents

Each item below is a command definition in this folder, grouped by subfolder.

### drafting

- [`check-congruity.md`](drafting/check-congruity.md): **`/drafting:check-congruity`** — reviews one recently edited file, passed as an optional path argument (defaulting to `plan.md` in `$ARTIFACTS_DIR` for Archon runs), for contradictions, inconsistencies, discrepancies, structural drift, duplicate claims, and missing connective logic. It itemizes findings, applies minimal fixes that preserve the author's voice and edit intent, then re-reads the file to verify the issues were resolved without introducing new ones.
- [`compare-docs.md`](drafting/compare-docs.md): **`/drafting:compare-docs`** — compares the document authored in the current conversation against another LLM's version at the required path argument. It rates both documents overall and section by section against the original instructions, proposes numbered surgical edits where the other version is stronger, performs root-cause analysis where both versions are weak, waits for explicit approval before applying edits, and treats the other LLM's file as read-only.
- [`seamless-edit.md`](drafting/seamless-edit.md): **`/drafting:seamless-edit`** — applies the edits agreed in the current conversation to a target document, from an optional free-form argument naming the file and any scoping notes. It edits surgically so the result reads as if the original author drafted the passages from the start, with no additive bloat, no in-file rationale, and no over-fitting to the incident that triggered the edit.

### git

- [`commit.md`](git/commit.md): **`/git:commit`** — creates an atomic Git commit in Conventional Commit format. It accepts optional file arguments, defaults to all current changes when no files are supplied, reviews `git status` and `git diff`, stages the intended files, composes a type/scope/description message, commits, and reports the resulting commit hash and file stats.

### implement

- [`execute.md`](implement/execute.md): **`/implement:execute`** — implements an existing plan from a required plan-file path. It reads the plan, executes tasks in order, follows the stated testing strategy, runs the validation commands exactly as specified, performs final verification, and reports completed tasks, tests added, validation results, and commit readiness.
- [`execution-audit.md`](implement/execution-audit.md): **`/implement:execution-audit`** — audits finished work against the plan it was built from. It accepts optional context naming the plan, commits, a commit range or a report name, and otherwise takes the plan from the conversation and the uncommitted changes from Git. It gives every plan item one status (implemented, partly implemented, missing, skipped, unverifiable or not applicable), grades each gap Critical, High, Medium or Low with a plan to close it, and writes the report for a reader who does not read code to `docs/reviews/<slug>-audit.md`. It changes no code and runs no tests, and the document-reviewer sub-agent reads the report before the command returns.

### helper

- [`explain-simply.md`](helper/explain-simply.md): **`/helper:explain-simply`** — rewrites the agent's most recent response, or the text passed as the argument, as a plain language explanation a 16-year-old can read. It avoids jargon, preserves the source meaning, includes one example only when necessary, and returns only the rewrite.
- [`log-response.md`](helper/log-response.md): **`/helper:log-response`** — appends a concise log entry for the previous AI response to `docs/backlog/response-log.md`. It takes no arguments, uses only the response text that was visible to the user, creates the log file when it is missing and never overwrites it, records the required metadata fields with each entry, reads the file back to verify the entry, and has the document-reviewer sub-agent read the log so that the new entry's wording can be corrected.
- [`revise-prompt.md`](helper/revise-prompt.md): **`/helper:revise-prompt`** — revises the user's original prompt into a self-contained, improved version based on feedback. It accepts optional feedback as the argument, falling back to the most recent user message, locates the original prompt and the AI response under critique, diagnoses the gap, plans surgical edits that preserve voice, structure, and intent, inlines context so the revised prompt stands alone, and returns only the revised prompt with no preamble or commentary.
- [`think-architect.md`](helper/think-architect.md): **`/helper:think-architect`** — answers the current technical question the way a senior software engineer and architect would. It accepts an optional question or context argument, falling back to the problem under discussion, inspects the existing architecture and decisions in the repository, reasons from first principles, builds the solution inside the current design or states deliberately what must change and why, and checks the result against common standards and best practice.
- [`wwcd.md`](helper/wwcd.md): **`/helper:wwcd`** — thinks through a decision the way a senior engineer would. It accepts optional guidance, takes the decision from the agent's previous response, checks whether it must be decided now and whether it is easy to reverse, scores every option against seven lenses (standards, architectural fit, lock-in, lifecycle fit, maintenance burden, maintainability by the owner, security and failure modes), recommends one option with up to two runners-up, and names the judgement that produced the recommendation so the owner can challenge it.

### meta

- [`create-agent.md`](meta/create-agent.md): **`/meta:create-agent`** — creates a new sub-agent in `.claude/agents/` from `.agents/templates/subagent_template.md`. It takes one required agent-spec argument plus optional invocation, handoff, and artifact mode arguments, validates those modes, enforces least-privilege tools, has the document-reviewer sub-agent read the new file, and produces a human-readable creation report.
- [`create-command.md`](meta/create-command.md): **`/meta:create-command`** — creates a new slash command in `.claude/commands/` from `.agents/templates/custom_command_template.md`. It accepts optional free-form context about desired behavior, constraints, or examples, enforces correct argument handling and a single output section, has the document-reviewer sub-agent read the new file, and keeps generated commands aligned with the repository's INPUT -> PROCESS -> OUTPUT standard.

### plan

- [`chart-course.md`](plan/chart-course.md): **`/plan:chart-course`** — takes one required problem-definition path followed by two or more solution-option paths, spawns exactly one Navigator sub-agent to evaluate and rank the options, verifies the Navigator's reported artifact exists at the path it reported, and reports only the invoked agent type plus the `status`, `summary` and `document_review.status` handoff fields before stopping.
- [`find-position.md`](plan/find-position.md): **`/plan:find-position`** — accepts an optional free-form comment as current-turn context, reviews the current conversation, extracts the best implicit or explicit problem definition, checks that explicit user decisions affecting the current loop are preserved during assessment, tests the definition against problem slicing, constraint articulation, outcome clarity, and solution separation, labels reasoning gaps, reports settled decisions used just before the verdict, and returns a cleaner replacement definition for downstream planning.
- [`fix-position.md`](plan/fix-position.md): **`/plan:fix-position`** — saves the previous AI response verbatim to a markdown file. It accepts an optional slug (inferring one from the response if omitted), normalises it to kebab-case, writes the response to `docs/options/<slug>-problem-definition.md`, creating the folder if needed, refuses to overwrite existing files without confirmation, and verifies the saved content by readback. The document-reviewer sub-agent then reads the saved file, and its findings correct the wording without changing what the definition says. The command reports the actual target file path.
- [`plan-feature.md`](plan/plan-feature.md): **`/plan:plan-feature`** — turns a feature request into an implementation-ready plan through feature understanding, codebase intelligence gathering, external documentation research, strategic analysis, and structured plan generation. The output includes the runtime environment the feature needs, context references, implementation phases, step-by-step tasks, testing strategy, validation commands, acceptance criteria, and a completion checklist. The plan is saved as `<slug>-plan.md` when the feature description names a file in `docs/options/`, and under a short descriptive name otherwise. The document-reviewer sub-agent reads the saved plan before the command reports.
- [`plan-review.md`](plan/plan-review.md): **`/plan:plan-review`** — reviews a feature plan from a required plan-file path before it is built, looking for the gaps its author cannot see. It checks every file, function and field the plan cites against the codebase, records findings in each of eighteen defect categories or states that a category has none, tags each finding material or cosmetic, and proposes a fix for each, preferring removal over addition and flagging any fix that would drop something the plan promises. It honours the findings the plan's NOTES section records as rejected in earlier rounds, writes the review to `docs/reviews/<plan-name>-plan-review.md` with a verdict of PASS, ITERATE or RE-SCOPE, has the document-reviewer sub-agent read it, and never edits the plan.
- [`plan-review-fix.md`](plan/plan-review-fix.md): **`/plan:plan-review-fix`** — applies a `/plan:plan-review` report, from a required review-file path, to the plan it reviewed. It judges each finding and its proposed fix separately, rejects findings the author's context shows are not gaps, refuses any fix that drops something the plan promises without the user's agreement, edits the plan in place, re-checks the plan's bookkeeping, and appends every declined finding to the rejection log in the plan's NOTES section so the next review round does not raise it again. It stops when the review passed the plan, when the plan must be re-scoped, or when, by the third round, findings keep returning in the same categories.
- [`prime.md`](plan/prime.md): **`/plan:prime`** — loads a project into the conversation before planning or implementation. It takes an optional feature to study closely, lists the files and recent commits, reads the PRD, the TAD, the root `README.md`, the configuration files and the entry points, maps each component the project's own documents name against the folders, reviews any stored-data definitions, and reports the project's state, its gaps against the PRD and TAD, and what is still unknown, with each finding marked Observed, Inferred or Unknown. It saves the report as `prime-<YYYY-MM-DD-HHMMSS>.md` and has the document-reviewer sub-agent read it. It names no project, folder or framework, so one file serves every kind of application.
- [`plot-routes.md`](plan/plot-routes.md): **`/plan:plot-routes`** — takes a required path to a problem-definition file, spawns multiple pathfinder sub-agents in parallel to produce independent solution options, saves each YAML report alongside the problem-definition file in `docs/options/` as `<slug>-option-<i>.yaml` (deriving the slug from the problem-definition filename), and presents a condensed preview without synthesis, ranking, merging, or interpretation.
- [`run-debate.md`](plan/run-debate.md): **`/plan:run-debate`** — takes two required absolute `.md` paths in the same folder (the problem file and a context file) and an optional `debate-config.json`, builds a `debate/` workspace beside them from symlinks so the originals stay the source of truth, and runs the orchestrate skill from the dialectic-agentic clone named by the environment variable `DIALECTIC_AGENTIC_DIR`.
- [`set-heading.md`](plan/set-heading.md): **`/plan:set-heading`** — takes the PRD path and the TAD path as required arguments and an architecture guide path as an optional third, infers the active prioritisation lens from those documents and recent `feat`/`fix` commits, then recommends one primary next feature and one alternate with the decision frame, signals, trade-offs, architecture fit, acceptance criteria, and done standard disclosed. It saves the report as `<slug>-heading.md` under a slug taken from the primary recommendation, has the document-reviewer sub-agent read it, and reminds the user that the slug is theirs to choose when `/plan:fix-position` runs.

### review

- [`change-review.md`](review/change-review.md): **`/review:change-review`** — establishes the scope of recent codebase changes via Git. It accepts optional context such as a commit hash or directory focus, inspects status, diffs, and logs as needed, compiles a deduplicated list of changed files, and writes a structured report to `docs/reviews/` for downstream review commands.
- [`combine-change-review.md`](review/combine-change-review.md): **`/review:combine-change-review`** — consumes two required `/change-review` report paths plus optional context. It validates both source reports, deduplicates changed files across them, preserves file-origin and source metadata, records any context-driven scope adjustments, and writes one downstream-compatible combined scope report to `docs/reviews/`.
- [`config-review.md`](review/config-review.md): **`/review:config-review`** — consumes a required `/change-review` report path and audits runtime configuration definitions and usage across the scoped changes. It checks environment variables, config modules, compose/Helm/CI settings, defaults, naming consistency, environment mismatches, and missing documentation, then writes a structured handoff for downstream fixes, named after the change-review report.
- [`deps-review.md`](review/deps-review.md): **`/review:deps-review`** — consumes a required `/change-review` report path and audits dependency manifests plus lockfiles against the changed files. It flags undeclared imports, stale or missing lockfiles, unpinned production dependencies, dev/prod mismatches, and required regeneration commands in a structured handoff, named after the change-review report.
- [`docs-review.md`](review/docs-review.md): **`/review:docs-review`** — consumes a required `/change-review` report path and audits `README.md` against the scoped codebase changes. It identifies undocumented features or APIs, outdated setup steps, renamed or removed references, and examples or paths that no longer match the repository, then writes section-level edit instructions as a structured handoff, named after the change-review report.
- [`hygiene-review.md`](review/hygiene-review.md): **`/review:hygiene-review`** — consumes a required `/change-review` report path, audits ignore lists, and scans changed files for plaintext secrets, API keys, tokens, and credentials. It halts and alerts the user when secrets are found, writing no file; otherwise it writes a structured handoff for ignore-list updates and related repository-local actions, named after the change-review report.
- [`review-handoff.md`](review/review-handoff.md): **`/review:review-handoff`** — takes a required `/change-review` report path and applies the complete set of structured review handoffs that `hygiene-review`, `deps-review`, `config-review`, and `docs-review` for that report. It validates source reviews, resolves overlapping instructions, applies file changes in grouped order, runs safe follow-up actions, and reports what changed without staging, committing, pushing, or merging.

### validate

- [`code-review-fix.md`](validate/code-review-fix.md): **`/validate:code-review-fix`** — consumes a required code review report path or manual issue description plus optional scope. It fixes actionable review findings one by one, adds or updates relevant tests, runs targeted verification and final validation, and writes a report of exactly what changed, named after the code review report when it worked from one, without staging, committing, pushing, or merging. The document-reviewer sub-agent reads the report before the command returns.
- [`validate.md`](validate/validate.md): **`/validate:validate`** — runs comprehensive project validation for any kind of project. It runs the checks the project writes into its Checks section in order, compares each with its expected result and stops anything a check started. With no checks written, it runs the project's own tests, type checks, linting and build. It then produces a summary report with each check's status and an overall PASS/FAIL health assessment. A codebase setup specification writes the checks for its stack at Step 12.

## Maintenance

When adding or changing commands in this folder:

- Keep this `README.md` list in sync with active command files and their subfolders.
- Keep active commands in the smallest appropriate folder.
- Each active command file should declare its argument contract, context to load, ordered process steps, decision discipline, and exactly one output section: Human-Readable Report or Structured Agent Handoff.
- Update the description here whenever a command's arguments, inputs, process, output format, output consumer, or file path changes.
